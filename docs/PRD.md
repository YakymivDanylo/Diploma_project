## Global Out-of-Scope / Optional Items

- **IPFS off-chain document storage** — evaluated as an optional/future extension only. The core system stores only the SHA-256 hash of a document on-chain; the source document file itself is NOT required to be persisted in IPFS (or anywhere else) for the diploma deliverable to be considered complete. If implemented, IPFS integration is additive and MUST NOT be a blocker for any acceptance criterion in Epics 2–5. See Epic 2 §Schema changes and Epic 4 §UI changes for the exact boundary.
- **RabbitMQ as inter-node transport** — evaluated and explicitly rejected. A centralized message broker contradicts the decentralized architecture under study and would weaken the validity of the Sybil-attack demonstration in Epic 5 (a broker becomes a single point of trust/failure that no longer reflects a peer-to-peer network). See Epic 3 §Non-goals. This decision is final for the scope of this thesis and should not be revisited without a new architectural review.

## Schema Recommendations (Reference)

This note summarizes, at a glance, the corrected entity set introduced by the architecture-review revisions (v1.1 and v1.2). Full field-level detail lives in each epic's own §Schema changes; this is a cross-epic index so the relationships are visible in one place.

- **`Block`** (Epic 2, revised in v1.1 and v1.2) — split into a hashed canonical preimage (`index`, `timestamp`, `previous_hash`, `merkle_root`, `proposer_id` (NEW in v1.2, present for BOTH PoW and PBFT), `algorithm`, `sealed_consensus` — PBFT's `sealed_consensus.primary_id` was REMOVED in v1.2 since `proposer_id` now covers proposer identity and having both was two sources of truth), the batch content (`document_records` — NOT part of the hashed preimage; its integrity is covered exclusively via `merkle_root`, v1.2 clarification), and attestation fields added after hashing (`block_hash`, `proposer_signature`, and — PBFT only — `commit_signatures[]`). See Epic 2 §Schema changes.
- **`DocumentRecord`** (Epic 2, unchanged in shape) — SHA-256 hash, issuer ID, timestamp, metadata, signature; optional `ipfs_cid` retained per the Global Out-of-Scope IPFS note. **v1.2 confirmed decision:** `signature` is always produced server-side by the node from its configured `IssuerKeyPair` at submission time (see Epic 3 §Schema changes / FR-22) — never supplied by the client/browser.
- **`IssuerKeyPair`** (Epic 2, NEW) — long-lived trust anchor, held and used exclusively by the backend node (never the browser/UI), used to sign `DocumentRecord`s; verified independently by Epic 4's verify flow and Epic 5's tamper tests. Replaces the single generic `KeyPair` entity from v1.0.
- **`NodeKeyPair`** (Epic 2, NEW) — per-node operational key used for `proposer_signature` on blocks and for peer/transport authentication in Epic 3. Independent from `IssuerKeyPair` — a compromised node key must never be usable to forge issued documents. Historical public keys survive rotation via the `ValidatorSet.retired_at` extension below.
- **`ValidatorSet`** (Epic 3, NEW; extended in v1.2, resolver contract clarified in v1.3) — static, boot-time-configured membership list (fixed `n`, `f`) used exclusively for PBFT quorum (2f+1) counting. Extended in v1.2 with a per-entry `retired_at` field so a retired/rotated validator's public key remains resolvable to verify OLD blocks' `proposer_signature`/`commit_signatures` after key rotation. **v1.3:** because a single-valued `node_id → public_key` map cannot hold both an old and a new key for the same `node_id`, the resolver built over `ValidatorSet` is time-aware — `resolve(node_id, at_timestamp)` (equivalently, `node_id → [{public_key, active from/until}]`) — selecting whichever key was active (per `retired_at`) at the given block's timestamp, so old blocks keep validating after rotation. Distinct from `PeerInfo`.
- **`IssuerRegistry`** (Epic 3, NEW in v1.2; scope broadened and resolver contract clarified in v1.3) — a **network-wide** `issuer_id → public_key` trust store covering every issuer identity used anywhere in the network — NOT merely "which issuer identity(ies) this node itself signs as." It serves two roles: (a) telling a node which issuer identity it signs new `DocumentRecord`s as (FR-22), and (b) supplying the issuer-half of the key resolver used by FR-6 to VERIFY `DocumentRecord` signatures found in OTHER nodes' blocks (see FR-6's new explicit signature-check step). **For this thesis's scope, the demo network uses a single shared issuer identity across all nodes** — the simplest legitimate choice for a prototype where every node represents the same issuing authority — while the schema remains a `issuer_id → public_key` map for generality (multi-issuer support is a natural, non-blocking extension). Like `ValidatorSet`, the issuer-half of the resolver is time-aware where an issuer key has a rotation history, for the same reason as above. Together with `ValidatorSet`, backs the key resolver INJECTED into Epic 2's chain-validation function (FR-6) — Epic 2 never looks up keys itself; the dependency direction is Epic 3 → Epic 2 only, keeping Epic 2 free of any network dependency.
- **`PeerInfo`** (Epic 3, unchanged in shape, clarified role) — dynamic, gossip-discovered peer registry used for connectivity/broadcast fan-out only; never used for quorum counting.

As the author of the diploma thesis, I want a structured comparison of blockchain construction principles and existing document-verification systems (e.g., Blockcerts) so that I can justify the architectural and cryptographic choices made in the custom blockchain engine (Epic 2) and consensus implementation (Epic 3).

## 2. Epic 2: Custom Blockchain Engine — Core (`Власний блокчейн-рушій (ядро)`)

### Feature description

A from-scratch Python implementation of the blockchain data structures and cryptographic primitives that make up a single node's local ledger: block structure, SHA-256 hashing, Merkle trees for batching multiple documents into one block, hash-chain integrity verification, and digital signatures (ECDSA or RSA via the `cryptography` library) so that an issuing authority can sign documents and/or blocks it issues. This epic delivers the core library that Epic 3 (consensus/network) and Epic 4 (web UI) both build on. It does not include peer-to-peer networking or consensus voting — those belong to Epic 3.

Design decisions here should reference Epic 1's findings (e.g., choice of hashing scheme, Merkle batching rationale).

**Revision note (v1.1, post architecture-review):** this epic now defines two independent key pairs (`IssuerKeyPair` for signing `DocumentRecord`s, `NodeKeyPair` for signing blocks — see FR-5/FR-8 and §Schema changes), a deterministic shared genesis block (FR-1), a canonical byte-encoding spec used everywhere hashing/signing occurs (FR-4), a collision-resistant Merkle construction with domain separation (FR-6), and a split between the hashed block preimage and attestation fields added after hashing (FR-2). These changes close architecture-review findings C-1, C-2, C-3, C-5, M-1, M-3, and M-4.

**Revision note (v1.2, second architecture-review round):** FR-2's hashed preimage now includes `proposer_id` for BOTH PoW and PBFT (PBFT's redundant `sealed_consensus.primary_id` is removed); FR-6 (chain/block validation) now explicitly receives an INJECTED key resolver, and — for PoW — an injected `expected_difficulty`, and — for PBFT — an injected `ValidatorSet`, all supplied by the caller (Epic 3 FR-23/FR-24), so Epic 2 never looks up keys or policy itself (dependency direction Epic 3 → Epic 2 only); FR-6 also gains a genuine PoW target/difficulty check, PBFT `commit_signatures` quorum verification, and an explicit genesis exemption; FR-1 now fully specifies `GENESIS_MERKLE_ROOT` as a fixed constant and genesis's sentinel `proposer_id`/`proposer_signature`; FR-5 now states the duplicate-document-hash rule at the batch level; and §Schema changes fixes the v1.1 contradiction where `document_records` was listed under "hashed preimage fields" despite being covered only via `merkle_root`. `POST /documents`'s issuer-signing contract (confirmed decision: the node signs server-side) is defined in Epic 3 FR-22 and referenced from FR-7/FR-8 below.

**Revision note (v1.3, architecture-review polish, FINAL):** FR-6's checklist gains an explicit step verifying each block's `DocumentRecord`(s) signature via the injected issuer resolver, failing with `failure_type = "signature"` on mismatch (previously only implied by the `failure_type` description, never stated as a checklist step) — see Epic 3 FR-23's broadened `IssuerRegistry`. FR-6's injected `node_id → public_key` resolver is clarified as time-aware — `resolve(node_id, at_timestamp)` — rather than single-valued, since a single-valued map cannot represent both a retired and an active key for the same `node_id`, which the rotation acceptance criteria (Epic 3 FR-23) already require. FR-5's duplicate-hash cross-reference to Epic 3 FR-22 is broadened to include the pending batch/mempool, not only finalized blocks. FR-1's genesis exemption note is made more concrete: genesis's placeholder `algorithm`/`sealed_consensus` values use a reserved literal (`algorithm = "genesis"`) that is explicitly exempt from algorithm-specific checks (the PoW difficulty/target check and the PBFT quorum check both skip genesis by definition).

### User story

As an issuing authority (e.g., a university registrar), I want to create digitally signed, tamper-evident records of documents I issue, batched and chained together with cryptographic hashes, so that anyone can later prove a specific document was issued by me at a specific point in time and has not been altered.

### Functional requirements

1. **Deterministic genesis block (closes C-1; fully specified in v1.2):** define a single genesis block (`index = 0`) shared byte-for-byte by every node, defined as a constant in project config — never computed per-node or left to node-local policy. The genesis block has: a fixed `timestamp` constant (defined once in config, e.g. `GENESIS_TIMESTAMP_MS`), `previous_hash = "0" * 64` (64 hex-zero characters), `merkle_root = GENESIS_MERKLE_ROOT` — a fixed hex constant defined once in config, conceptually the domain-separated hash of zero leaves per the FR-5 Merkle spec (the exact hex value is computed once at implementation time and hardcoded/configured identically on every node — never recomputed per node), the same `algorithm`/`sealed_consensus` placeholder values on every node — **`algorithm` is set to the reserved literal `"genesis"`** (never `"pow"` or `"pbft"`), and `sealed_consensus` is an empty/placeholder object; this reserved literal is explicitly exempt from every algorithm-specific check in FR-6 (the PoW difficulty/target check and the PBFT quorum check both skip a block whose `algorithm == "genesis"` by definition, not merely "block index 0" as an implicit special case) — and sentinel values `proposer_id = null`/empty and `proposer_signature = null`/empty (genesis has no proposer — FR-6 explicitly exempts the genesis block from the `proposer_signature`/`proposer_id` check by definition). Any "per-node genesis policy" is explicitly disallowed — all nodes in a network MUST start from byte-identical genesis blocks, verified by comparing `block_hash` at boot. **The chain is never empty:** genesis (`index = 0`) exists in every node's local chain from process startup onward; "zero blocks" or "no genesis yet" is not a valid chain state anywhere in this system (see also Epic 3 FR-3/FR-16, which always operate on a chain of at least one block).
2. **Block structure — hashed preimage vs. attestations (closes C-2; extended in v1.2 to add `proposer_id`):** define a `Block` structure with clearly separated field groups:
   - **Hashed canonical preimage** (the only fields covered by `block_hash`): `index`, `timestamp`, `previous_hash`, `merkle_root`, `proposer_id` (the `node_id` of the block's proposer — NEW in v1.2, present for BOTH PoW and PBFT so proposer identity is always covered by the hash and always checked by FR-6's signature verification), `algorithm` (`"pow"` | `"pbft"`), and `sealed_consensus` (PoW: `{nonce, difficulty}`; PBFT: `{view_number}` — `primary_id` is intentionally NOT duplicated here in v1.2; `proposer_id` above is the single source of truth for proposer identity in both algorithms).
   - **`document_records`** (the batch itself): stored with the block but NOT part of the hashed preimage — its integrity is covered exclusively via `merkle_root` (see §Schema changes for the precise grouping, v1.2 fix).
   - **Attestation fields** (outside the hash preimage, attached after hashing): `block_hash` itself, `proposer_signature` (NEW — see FR-8), and — PBFT only — `commit_signatures[]` (attestations from ≥ 2f+1 validators over the ValidatorSet defined in Epic 3, collected strictly after the block is hashed; never part of the preimage).
3. Compute all hashes using SHA-256.
4. **Canonical serialization spec (closes M-3):** define and document a single canonical byte-encoding used everywhere a hash or signature is computed (block preimage, `DocumentRecord`, Merkle leaves): JSON object keys sorted lexicographically, no insignificant whitespace, UTF-8 encoding, all timestamps encoded as integer epoch-milliseconds (never ISO strings or floats), and all hash/signature/public-key fields encoded as lowercase hex. Provide a fixed set of test vectors (input struct → expected canonical bytes → expected SHA-256 hash) that all hashing/signing code paths (Epic 2 core, Epic 3 node code) must produce identically.
5. **Merkle tree with domain separation (closes C-5):** implement a Merkle tree that takes a batch of one or more document-hash entries (a "document record" = SHA-256 hash of the document content + minimal metadata such as issuer ID and issuance timestamp) and produces a single Merkle root for inclusion in a block, using RFC 6962-style domain separation to prevent the CVE-2012-2459-class second-preimage/duplication collision: leaf hash = `H(0x00 || leaf_bytes)`, internal node hash = `H(0x01 || left_hash || right_hash)`. For an odd number of nodes at a tree level, the tree is NOT balanced by duplicating the last leaf; the unpaired node is carried up unchanged to the next level (standard unbalanced-tree promotion), preserving the domain-separated construction. **Duplicate-hash policy at batch level (v1.2; cross-reference broadened in v1.3):** batch construction MUST reject (never silently deduplicate or accept) a batch containing the same `document_hash` twice. See Epic 3 FR-22 for the single, authoritative statement of the full duplicate-document-hash policy (a hash already finalized anywhere in the chain, OR already present in the current pending batch/mempool, is also rejected — v1.3 broadens this from "finalized chain only") — Epic 3's `POST /documents` enforces the chain-wide-plus-pending check at submission time, before batch/Merkle construction is invoked; this FR covers only the within-batch case.
6. **Hash-chain integrity verification with failure classification, injected key resolver, and PoW/PBFT-specific checks (closes M-1, M-4; extended in v1.2 to close second-round CRITICAL/MAJOR findings on key lookup, PoW verification, and PBFT quorum-at-sync; resolver contract and checklist step added in v1.3):** given a full chain (ordered list of blocks) AND an INJECTED key resolver supplied by the caller as a parameter — a **time-aware** `node_id → public_key` resolver, e.g. `resolve_node_key(node_id, at_timestamp) → public_key` (equivalently, `node_id → [{public_key, valid_from, valid_until}]`), covering current AND retired `NodeKeyPair` public keys and selecting whichever key was active at the given block's timestamp (see Epic 3 FR-23's `ValidatorSet.retired_at` extension) — and a likewise time-aware `resolve_issuer_key(issuer_id, at_timestamp) → public_key` (see Epic 3 FR-23's `IssuerRegistry`) — a function returns whether the chain is valid. **v1.3 clarification:** a single-valued `node_id → public_key` (or `issuer_id → public_key`) map cannot represent both a retired and a currently-active key for the same identity, so the resolver contract MUST accept a timestamp and pick the key active at that point in time; this is required for the FR-23 key-rotation acceptance criteria (old blocks must keep validating after a key rotates) to be satisfiable at all. **This function never looks up keys itself** (no registry access, no network call); the resolver is built and injected by the caller (Epic 3), keeping Epic 2 free of any network dependency and preserving the dependency direction Epic 3 → Epic 2 only (Epic 2 must never import or depend on Epic 3). For PoW chains, the caller similarly injects an `expected_difficulty` value (see Epic 3 FR-24); for PBFT chains, the caller injects the `ValidatorSet` (`n`, `f`, and the node-key resolver above) needed to compute the 2f+1 quorum size.

   The function checks, for every block except genesis (see the genesis exemption below): each block's `previous_hash` matches the actual hash of the prior block; each block's stored `block_hash` matches a fresh recomputation over the canonical preimage (FR-2, FR-4); each block's `merkle_root` matches a fresh recomputation over its document records (FR-5); each block's `proposer_signature` verifies against the public key returned by `resolve_node_key(proposer_id, block.timestamp)` (closes M-1 — block-level tamper detection now covers `timestamp`, `index`, `previous_hash`, `merkle_root`, `proposer_id`, and consensus fields, not just `DocumentRecord` fields); **(NEW in v1.3) each `DocumentRecord` in the block's batch has its `signature` verified against `resolve_issuer_key(document_record.issuer_id, block.timestamp)`** — this is an explicit per-block checklist step (previously only implied by the `"signature"` failure-type description below, never stated as a check the function actually performs), failing with `failure_type = "signature"` on any mismatch; `Block.timestamp` is non-decreasing across the chain (a block's timestamp must be ≥ its predecessor's); **for PoW blocks (`algorithm == "pow"`)**: `block_hash`, treated as an unsigned integer, numerically satisfies the target derived from `sealed_consensus.difficulty` (a genuine proof-of-work check, not merely a hash-match check), AND `sealed_consensus.difficulty` equals the injected `expected_difficulty` (an arbitrary self-declared difficulty is rejected — see Epic 3 FR-24); **for PBFT blocks (`algorithm == "pbft"`)**: `commit_signatures[]` contains signatures from at least `2f+1` distinct `ValidatorSet` members (resolved via `resolve_node_key(..., block.timestamp)`), each validly signing the block's canonical preimage — this is the SAME check whether the chain arrived via a live consensus round or via chain-sync/full-revalidation/the `GET /node/info` validity cache (see Epic 3 FR-25).

   **Genesis exemption:** the genesis block (`index = 0`), identified by its reserved `algorithm = "genesis"` literal (see FR-1), is exempt from the `proposer_signature`/`proposer_id` check by definition (see Epic 2 FR-1's sentinel `proposer_id`/`proposer_signature` values) and from every algorithm-specific check (the PoW difficulty/target check and the PBFT quorum check both skip it), and is instead checked only for byte-identical equality against the shared `GENESIS_TIMESTAMP_MS`/`GENESIS_MERKLE_ROOT`/`previous_hash` constants (FR-1).

   When validation fails, the result includes a `failure_type` field with one of: `"hash"` (block_hash mismatch), `"link"` (previous_hash mismatch), `"merkle"` (merkle_root mismatch), `"signature"` (proposer_signature or document-record signature invalid), `"difficulty"` (NEW in v1.2 — PoW target not met, or `difficulty` does not match `expected_difficulty`), `"quorum"` (NEW in v1.2 — PBFT `commit_signatures[]` does not meet the 2f+1 threshold over the injected `ValidatorSet`), `"structural"` (e.g. non-monotonic timestamp, malformed preimage), plus the index of the first failing block. The chain's trust guarantee is reframed as **"this record existed no later than the block that contains it"** — not an absolute, unfalsifiable issuance-time claim — given the timestamp-monotonicity-only guarantee.
7. Implement digital signing of document records using ECDSA (P-256) or RSA (minimum 2048-bit) via the `cryptography` library. **The `IssuerKeyPair` private key is held server-side only, by the backend node**, configured at node startup on behalf of the institution the node represents; the node signs each `DocumentRecord` at the moment a document is submitted (see Epic 3 FR-22 for the exact request/response shape). The browser/UI never generates, holds, or transmits `IssuerKeyPair` private-key material — this is a confirmed architectural decision, not an open question (see FR-8 and §Schema changes for the key-pair split).
8. **Split issuer key from node key (closes C-3):** define two independent key-pair types:
   - `IssuerKeyPair` — the long-lived trust anchor, held by the backend node (never by the browser/UI — see FR-7). Its private key signs `DocumentRecord`s server-side at submission time (FR-7; Epic 3 FR-22); its public key is what Epic 4's verify flow and Epic 5's tamper tests check signatures against (see Epic 5 §Functional requirements, M-2).
   - `NodeKeyPair` — an operational, per-node key. Its private key produces `proposer_signature` over a block's canonical preimage (FR-2, FR-6) and authenticates the node at the peer/transport layer in Epic 3. A compromised `NodeKeyPair` must never allow forging a `DocumentRecord` signature, and a compromised `IssuerKeyPair` must never be required for a node to participate in consensus. When a `NodeKeyPair` is rotated, its OLD public key remains resolvable via Epic 3's extended `ValidatorSet` (`retired_at` field, FR-23), so historical blocks it proposed/attested to remain verifiable by FR-6 after rotation.
   Implement signature verification for both key types: given a signed payload (document record or block canonical preimage), its signature, and the relevant public key, return whether the signature is valid.
9. Provide a Merkle-inclusion proof generator and verifier: given a document hash and a block's Merkle tree, produce a proof (sibling hash path, domain-separated per FR-5) and a function to verify that proof against the block's stored Merkle root, without needing the full batch of documents.
10. Provide a way to detect tampering: mutating any field of a previously issued document record (or its hash), or any field of a block's canonical preimage (index, timestamp, previous_hash, merkle_root, proposer_id, consensus fields), must cause hash-chain verification (FR-6) and/or Merkle-proof verification (FR-9) to fail, with the appropriate `failure_type` reported.
11. Persist the chain, the `IssuerKeyPair`, and the `NodeKeyPair` to local storage (file-based, e.g., JSON/SQLite), each in its own logical store, so a node's state survives a process restart.

### Non-functional requirements

- Hashing and signature operations must use only well-reviewed primitives from the `cryptography` library (or Python's `hashlib` for SHA-256) — no custom/home-grown cryptographic algorithms.
- Private keys (both `IssuerKeyPair` and `NodeKeyPair`) must never be logged or written to plaintext output outside of their designated key storage files.
- Core library functions (hashing, Merkle tree build/verify, chain validation) must run in-process with no network dependency, so they can be unit-tested in isolation from Epic 3's networking code. Chain validation's key resolver, `expected_difficulty`, and `ValidatorSet` parameters (FR-6) are plain injected data (dicts/callables/values) supplied by the caller — never fetched over the network by Epic 2 itself — so this isolation-from-networking property holds even with the v1.2 injected-parameter extension.
- Merkle tree and chain validation must complete in better than O(n²) time relative to the number of documents/blocks, so the demonstration network in Epic 3 remains responsive at the batch sizes used for the thesis (tens to low hundreds of documents/blocks).
- The canonical serialization spec (FR-4) must be implemented once as a shared utility and imported by every hashing/signing call site (Epic 2 core and Epic 3 node code) — no parallel/duplicated encoding logic, to prevent hash-mismatch bugs across nodes.

### Acceptance criteria

- [ ] All nodes in a freshly started network compute an identical genesis `block_hash` with no configuration other than the shared constants (verifies C-1).
- [ ] Given a batch of N document hashes, the system produces one Merkle root (via the domain-separated construction) and N valid inclusion proofs, each independently verifiable.
- [ ] Given a chain of blocks, tampering with any single block's content (document record, previous-hash field, timestamp, or any other canonical-preimage field) causes chain validation to return invalid, reports the correct `failure_type` (`"hash"`/`"link"`/`"merkle"`/`"signature"`/`"structural"`), and identifies the point of failure (block index).
- [ ] Tampering with a block's `timestamp`, `index`, or `previous_hash` alone (with no document-record change) is detected via `proposer_signature` verification failure — demonstrating block-level tamper detection independent of document-record signatures (verifies M-1 closure).
- [ ] A document record signed with an `IssuerKeyPair` private key verifies successfully against the matching public key, and fails verification if the record or signature is altered by a single byte.
- [ ] A block signed with a `NodeKeyPair` private key (`proposer_signature`) verifies successfully against the matching node public key, and fails if any canonical-preimage field is altered by a single byte.
- [ ] Two independently generated document/block payloads that canonicalize identically (per FR-4 test vectors) produce byte-identical serialized output and identical hashes across two separate implementations/runs.
- [ ] A chain with a decreasing `Block.timestamp` between consecutive blocks is rejected by validation with `failure_type = "structural"`.
- [ ] Chain state, `IssuerKeyPair`, and `NodeKeyPair` persist across a process restart and reload to an identical, verifiable state.
- [ ] Unit tests cover: genesis-block equality across nodes, block hashing (preimage vs. attestation split), Merkle root computation (domain-separated), Merkle proof verify (valid + tampered), chain validation (valid + tampered, all `failure_type` values), issuer signature sign/verify (valid + tampered), node/proposer signature sign/verify (valid + tampered), canonical-encoding test vectors.
- [ ] Chain validation (FR-6) is called with an injected key resolver and, for PoW, an injected `expected_difficulty`; a chain containing a block whose `block_hash` does not numerically satisfy its own declared `difficulty`'s target is rejected with `failure_type = "difficulty"`, and a chain where `sealed_consensus.difficulty` differs from the injected `expected_difficulty` is likewise rejected with `failure_type = "difficulty"`.
- [ ] A PBFT chain block whose `commit_signatures[]` does not reach the 2f+1 threshold over the injected `ValidatorSet` is rejected with `failure_type = "quorum"`.
- [ ] The genesis block passes FR-6 validation despite having sentinel `proposer_id`/`proposer_signature` values (verifies the genesis exemption).
- [ ] Attempting to construct a Merkle batch containing the same `document_hash` twice is rejected (verifies FR-5's duplicate-within-batch check).

### Schema changes

New local data model (introduced fresh, no prior schema exists). **Revised in v1.1 per architecture review** — see Schema Recommendations note above for the cross-epic summary.

- `DocumentRecord`: `document_hash` (SHA-256 hex), `issuer_id`, `issued_at` (integer epoch-ms, per FR-4 canonical encoding), `metadata` (free-form, e.g., recipient name/ID — non-PII where possible; size-bounded per Epic 3 M-11), `signature` (produced with `IssuerKeyPair`, server-side, by the node — see FR-7 and Epic 3 FR-22; never supplied by the client).
- `Block` (revised — hashed preimage vs. attestations, closes C-2; further clarified in v1.2 to remove a contradictory grouping and add `proposer_id`):
  - **Hashed preimage fields** (the ONLY fields covered by `block_hash`): `index`, `timestamp` (epoch-ms), `previous_hash`, `merkle_root`, `proposer_id` (NEW in v1.2 — the `node_id` of the node/issuer producing this block; see FR-2/FR-6 and Epic 3 FR-23), `algorithm` (`"pow"` | `"pbft"`), `sealed_consensus` (PoW: `{nonce, difficulty}`; PBFT: `{view_number}` — `primary_id` removed in v1.2, since `proposer_id` above now covers proposer identity; keeping both was two sources of truth for the same fact).
  - **`document_records`** (batch content — NOT part of the hashed preimage): stored alongside the block for retrieval/display, but its integrity is covered exclusively via `merkle_root` (FR-5/FR-9), never by being directly hashed into `block_hash`. This is grouped separately from both the hashed preimage and the attestation fields below, fixing the v1.1 ambiguity where it was listed under "hashed preimage fields" with a contradicting parenthetical.
  - **Attestation fields** (outside the hash, attached after hashing): `block_hash`, `proposer_signature` (NodeKeyPair signature over the canonical preimage), `commit_signatures[]` (PBFT only — populated by Epic 3, attestations from ≥2f+1 `ValidatorSet` members, never part of the preimage).
- `Chain`: ordered list of `Block`, starting from the deterministic genesis block (FR-1), persisted to local file storage (JSON or SQLite — implementation choice deferred to the planner/architect). The chain is never empty — genesis (`index = 0`) is present from node startup.
- `IssuerKeyPair` (NEW, replaces v1.0's generic `KeyPair`): the trust-anchor key pair. Signs `DocumentRecord`s. Persisted to a local key store file, separate from chain data and from `NodeKeyPair`. Held and used exclusively by the backend node process (configured at node startup, on behalf of the institution) — never generated, transmitted to, or held by the browser/UI (see FR-7, Epic 3 FR-22).
- `NodeKeyPair` (NEW): the per-node operational key pair. Signs blocks (`proposer_signature`) and authenticates the node in Epic 3's peer/transport layer. Persisted separately from `IssuerKeyPair`. Historical public keys of retired/rotated `NodeKeyPair`s remain resolvable via Epic 3's `ValidatorSet.retired_at` extension (FR-23), so old blocks' `proposer_signature` stays verifiable after rotation.
- Note on IPFS (optional/future, see Global Out-of-Scope): `DocumentRecord` may optionally carry an `ipfs_cid` field for the off-chain file pointer. This field is NOT required for Epic 2 acceptance and must default to null/absent if unused. Retained unchanged in v1.1.

## 3. Epic 3: Consensus & Node Network (`Консенсус та мережа вузлів`)

### Feature description

Extends the Epic 2 core into a multi-node network. Implements and compares two consensus algorithms — Proof of Work (PoW) and Practical Byzantine Fault Tolerance (PBFT) — evaluated for block-finalization speed and resistance to attacks (further exercised in Epic 5). Nodes communicate via REST (peer registration, chain synchronization) and WebSocket (new-block broadcast, PBFT prepare/commit message rounds). The network is deployed as genuinely separate node instances using Docker and docker-compose, so the demonstration reflects real inter-process/inter-container communication rather than a single-process simulation.

**Revision note (v1.1, post architecture-review):** this epic now introduces a static, boot-time `ValidatorSet` used exclusively for PBFT quorum counting, kept strictly separate from the dynamic `PeerInfo` gossip registry (closes C-4 — central to the thesis's PoW-vs-PBFT Sybil-resistance comparison: PBFT resists Sybil via closed membership, PoW resists it via hash power, not node count). It also adds a `PeerConnectionManager` component (M-5), documents the PBFT view-change as an intentional simplification (M-6), clarifies quorum-counting semantics (M-7), distinguishes crash vs. Byzantine fault reporting (M-9), adds/renames several endpoints (M-10 and MINOR items), and adds an error envelope, request validation, and CORS requirements (M-11, M-12).

**Revision note (v1.2, second architecture-review round):** `POST /documents` is now explicitly unsigned — `{hash, metadata}` — with the node signing the resulting `DocumentRecord` server-side using its configured `IssuerKeyPair` (confirmed architectural decision; see FR-22), and a single duplicate-document-hash policy is stated there. Adds `IssuerRegistry` and a `retired_at`-extended `ValidatorSet` backing an injected key resolver consumed by Epic 2's FR-6 (FR-23). Adds injected PoW difficulty verification (FR-24). Makes explicit that PBFT `commit_signatures[]` quorum verification is the same checklist at proposal-time AND chain-sync-time (FR-25). Adds a continuously-updated validity cache backing `GET /node/info` (FR-26). Restricts the FR-17 fork tie-break to PoW only, treating same-height PBFT forks as a Byzantine-fault event. Fixes two stale internal cross-references in FR-3 (`FR-14` → `FR-18` for pagination, `FR-14` → `FR-16` for full-revalidation).

**Revision note (v1.3, architecture-review polish, FINAL):** `IssuerRegistry` (FR-23) is redefined from "which issuer identity(ies) this node signs as" into a **network-wide** `issuer_id → public_key` trust store covering every issuer identity used anywhere in the network, since the same registry also backs verification of OTHER nodes' `DocumentRecord` signatures (consumed by Epic 2 FR-6's new explicit signature-check step); for this thesis's scope the demo network uses a single shared issuer identity across all nodes (the schema stays a map for generality). The key resolver injected into Epic 2 FR-6 (FR-23) is now explicitly time-aware (`resolve(node_id or issuer_id, at_timestamp)`) so it can actually satisfy the key-rotation acceptance criteria below — a single-valued map cannot. FR-22's duplicate-hash rejection is broadened to also reject a hash already present in the current pending batch/mempool, not only a finalized block. FR-24 adds a note that changing the configured difficulty requires starting from a fresh chain. The schema section's stray `validator_id` field is renamed `node_id` for consistency with FR-6/FR-23/FR-11.

### User story

As the thesis author, I want a running multi-node network where nodes independently propose, validate, and agree on new blocks using either PoW or PBFT, so that I can measure and compare the two consensus algorithms' finalization latency and their behavior under simulated attacks.

### Functional requirements

1. Each node runs as an independent process (in its own Docker container) exposing a REST API and a WebSocket endpoint, built on FastAPI/asyncio per the project's tech stack.
2. REST: peer registration — a node can register itself with one or more known peers and receive back the peer's current peer list (basic gossip-style discovery). This registry is `PeerInfo`-only (connectivity/broadcast), never used for consensus quorum counting (see FR-11).
3. REST: chain synchronization — a node can request another node's full chain (or a range of blocks, see FR-18) and apply the standard longest-valid-chain (or, for PBFT, latest-finalized-height) rule to resolve conflicts, using Epic 2's chain-validation function invoked with this node's injected key resolver/`expected_difficulty`/`ValidatorSet` (FR-23/FR-24) and the SAME full checklist used at proposal-time, including PBFT `commit_signatures[]` quorum verification (FR-25), with the full-revalidation rule in FR-16 (closes M-14). The chain returned/compared is never empty — every node's chain includes at least the genesis block (Epic 2 FR-1) from process startup.
4. WebSocket: new-block broadcast — when a node finalizes a new block, it broadcasts the block to all connected peers in real time.
5. Implement Proof of Work: configurable difficulty target; a node must find a nonce such that the block hash meets the target before broadcasting the block as a candidate.
6. Implement PBFT: a per-round primary/leader proposes a block; nodes exchange `pre-prepare` → `prepare` → `commit` messages over WebSocket; a block is finalized once a node observes ≥ 2f+1 matching `commit` messages, counted exclusively over the `ValidatorSet` (see FR-11), for a cluster tolerating f faulty nodes.
7. The consensus algorithm used by a given running network is configurable at node startup (environment variable or config file), so the same codebase can run in either mode for comparison.
8. Provide a `docker-compose.yml` (or equivalent) that spins up a configurable number of node containers (minimum 4, to support PBFT's f=1 fault tolerance) on a shared Docker network, each reachable at a distinct host:port.
9. Expose a REST endpoint returning node-local metrics needed for later comparison: block finalization timestamps, per-block time-to-finalize, and (for PoW) hash attempts and per-node hash-rate (see Epic 5 M-8), (for PBFT) message round-trip counts.
10. Nodes reject and do not propagate blocks that fail Epic 2's hash-chain, `proposer_signature`, or (PBFT) `commit_signatures` validation.
11. **Static `ValidatorSet`, separate from `PeerInfo` (closes C-4):** each node is configured at startup with a `ValidatorSet` — a fixed, static list of validator node identities/public keys with a fixed `n` (size) and derived `f` (`n ≥ 3f + 1`), logged at boot. The `ValidatorSet` is completely independent from the dynamic `PeerInfo` peer-discovery registry (FR-2). PBFT quorum counting (2f+1 `prepare`/`commit` messages) is computed exclusively over the `ValidatorSet` — never over however many peers happen to be currently registered in `PeerInfo`. This is a core requirement of the thesis: it is what makes PBFT's Sybil-resistance closed-membership-based (an attacker who registers as a `PeerInfo` peer gains no consensus voting weight), structurally distinct from PoW's hash-power-based Sybil-resistance (see Epic 5 M-8).
12. **`PeerConnectionManager` (closes M-5):** each node implements a connection-management component that acts as both a WebSocket server (accepting inbound connections) and a WebSocket client (maintaining outbound connections to every peer in `PeerInfo` and every member of `ValidatorSet`), so that fan-out broadcast (new-block broadcast, PBFT all-to-all `prepare`/`commit` messaging) reaches all parties regardless of which side initiated the connection. The component must reconnect with backoff (e.g., exponential, capped) on connection loss, and must expose connection health per peer for use by FR-9's metrics and the `GET /node/info` endpoint (FR-15).
13. **Simplified PBFT view-change, documented as intentional (closes M-6):** implement view-change as a deliberately simplified deterministic round-robin primary election: `primary = view_number mod n` (over the `ValidatorSet`), triggered by a timeout when the current primary fails to drive a round to completion. This implementation explicitly does NOT include a state-transfer, checkpoint, or watermark protocol (as found in full PBFT specifications). This is documented here as an intentional, scoped-down simplification appropriate for the thesis prototype — not an undocumented gap — and must be called out as such in the thesis write-up and in code comments at the view-change implementation site.
14. **Quorum-counting rule, made explicit (closes M-7):** the primary's own `pre-prepare` message counts as its implicit vote toward its own `prepare` quorum (standard PBFT semantics: yes) — i.e., the primary does not need to separately send itself a `prepare` message to count toward the 2f+1 threshold for its own proposal. This must be implemented and documented unambiguously at the quorum-counting code site.
15. **Crash vs. Byzantine fault distinction (closes M-9):** the system must distinguish and separately report two failure classes: (a) *crash faults* — up to f nodes stopped/unresponsive (a liveness concern: consensus may stall but no wrong block is ever finalized), and (b) *Byzantine faults* — up to f nodes behaving maliciously/equivocating, e.g. sending conflicting `prepare`/`commit` votes to different peers (a safety concern). These are tested as distinct scenarios in Epic 5 and must be distinguishable in `GET /node/info`'s `quorum_status` field and in metrics/logs (e.g., "peer unreachable" vs. "equivocation detected").
16. **Full chain-revalidation on fork divergence (closes M-14):** when resolving a chain-sync conflict (FR-3), if the incoming chain diverges from the local chain at some block before the local tip (i.e., it is not a simple append), the node must run Epic 2's full chain-validation function over the entire incoming chain from genesis (or at minimum from the divergence point back through genesis-linked ancestry) before accepting it — not merely validate the new blocks incrementally from the local tip forward. Incremental from-the-tip validation is only sufficient when the incoming chain is a strict, non-diverging extension of the local chain. This full revalidation uses the same injected resolver/checklist as FR-25 (including PBFT `commit_signatures[]` quorum verification), not a lighter check.
17. **Deterministic fork tie-break — PoW only (closes second-round MAJOR — tie-break scope):** the "select the chain whose tip has the lowest `block_hash`" (treated as an unsigned integer/lexicographic hex comparison) deterministic tie-break rule applies EXCLUSIVELY to PoW chains, where two competing chains of equal length are an expected, benign occurrence. "First-observed" or any other node-local/order-dependent tie-break remains explicitly disallowed for PoW, since it would make different nodes converge on different chains under identical global state. **For PBFT, this tie-break rule MUST NOT be applied**: because PBFT finalization already requires a 2f+1 quorum, two different blocks both being finalized at the same height is not a normal fork — it is only possible if the quorum was corrupted (e.g., equivocating validators, see FR-15). A node that observes two differently-finalized blocks at the same height on a PBFT chain MUST NOT silently pick one; it MUST report/log the condition as a Byzantine-fault/safety-violation event (per FR-15's Byzantine-fault reporting) and surface it via `quorum_status` in `GET /node/info` (FR-20).
18. **`GET /chain` pagination:** `GET /chain` must support `?from=<index>&to=<index>` query parameters to return a bounded range of blocks, with a server-enforced maximum page size (returning fewer blocks than requested, or a validation error, if the requested range exceeds the max — never an unbounded full-chain dump on a large chain).
19. **Error envelope and input validation (closes M-11):** every Epic 3 REST endpoint returns errors using a single JSON envelope shape: `{"error": {"code": "<machine_readable_code>", "message": "<human_readable_message>", "details": {...}}}`. All request bodies are validated with Pydantic models; hash-valued fields (`document_hash`, `previous_hash`, `block_hash`, etc.) are validated against the pattern `^[0-9a-f]{64}$`. `DocumentRecord.metadata` has an explicit, server-enforced maximum size (e.g., a byte-length cap defined in config) — unbounded metadata is rejected with a validation error, since metadata is broadcast to every peer and unbounded size is a DoS/amplification vector.
20. **`GET /node/info` (closes M-10):** new endpoint returning `{node_id, algorithm, n, f, node_public_key, tip_index, chain_valid, first_invalid_index, quorum_status}` — a single-call node health/identity summary used by Epic 4's UI and Epic 5's attack scripts, and distinguishing crash vs. Byzantine quorum-loss states per FR-15. `chain_valid`/`first_invalid_index` are read from the continuously-updated validity cache described in FR-26, not recomputed by a full chain revalidation on every call.
21. **Document lookup endpoint, relocated from Epic 4 (closes M-10 endpoint-ownership item):** `GET /documents/{hash}` — looks up a `DocumentRecord` by its SHA-256 hash across the local chain, returning issuer identity, timestamp, containing block index, and Merkle-proof data if found, and an HTTP 404 (via the FR-19 error envelope) if not found — explicitly distinguishing "not found" from a server error, which the prior `GET /documents/search?hash=` query-parameter shape (Epic 4 v1.0) did not.
22. **`POST /documents` — unsigned submission, server-side issuer signing, and duplicate-hash policy (renamed from `POST /blocks/submit` in v1.1; issuance contract and duplicate policy finalized in v1.2 — confirmed architectural decision; duplicate-check scope broadened in v1.3):** the request body is UNSIGNED: `{hash, metadata}` (`hash` = SHA-256 hex of the document content, computed client-side by Epic 4's Issue page per Epic 4 FR-1; `metadata` per Epic 3 FR-19's size cap). The endpoint does NOT accept a pre-signed `DocumentRecord` or any client-supplied signature — the browser/UI never touches `IssuerKeyPair` private-key material. On receiving a valid request, the node: (a) rejects with `409 Conflict` (via the FR-19 error envelope) if `hash` already appears in ANY finalized block anywhere in the local chain **OR is already present in the node's current pending batch/mempool awaiting inclusion in a not-yet-finalized block (v1.3 — broadened from "finalized block" only, to match the batch-construction rule in Epic 2 FR-5 and to cover concurrent-submission races before a block is finalized)** — this is the single, authoritative duplicate-document-hash rule for the whole system; once finalized, a hash can never appear again, and it also cannot be queued twice while still pending (no "return the earliest match" behavior, no silent deduplication — see Epic 2 FR-5's batch-level duplicate check and Epic 4's reliance on this rejection rather than any dedup UI); (b) otherwise, assembles `{document_hash: hash, issuer_id: <this node's configured IssuerRegistry issuer_id, FR-23>, issued_at: <now, epoch-ms>, metadata}` and signs it with the node's configured `IssuerKeyPair` private key (FR-7/FR-8 in Epic 2) to produce the full signed `DocumentRecord`, before including it in a block (PoW: triggers local mining; PBFT: triggers a proposal round if the node is primary).
23. **Key registries backing the injected key resolver (closes second-round CRITICAL — key registries; `IssuerRegistry` scope broadened and resolver made time-aware in v1.3):** each node loads two config-driven registries at boot: (a) `IssuerRegistry` — a **network-wide** `issuer_id → public_key` trust store covering every issuer identity used anywhere in the network, not merely "which issuer identity(ies) this node itself signs as." It serves two roles: it tells this node which `issuer_id` to sign new `DocumentRecord`s as when producing them via `POST /documents` (FR-22), AND it supplies the issuer-half of the resolver used by Epic 2's FR-6 to VERIFY `DocumentRecord` signatures found in blocks received from any node in the network (FR-6's explicit per-block signature-check step). **For this thesis's scope, the demo network uses a single shared issuer identity configured identically across all nodes** — the simplest legitimate choice for a prototype representing one issuing authority — while the registry's schema remains a general `issuer_id → public_key` map to support future multi-issuer extension without a contract change; and (b) an extension of `ValidatorSet` (FR-11) with a per-entry `retired_at` (nullable epoch-ms) field — when a validator's `NodeKeyPair` is rotated or the validator is removed, its OLD entry is marked `retired_at` rather than deleted, so its public key remains resolvable for verifying `proposer_signature`/`commit_signatures` on blocks it produced/attested to BEFORE the rotation. **Resolver contract is time-aware (v1.3):** because a single-valued `node_id → public_key` (or `issuer_id → public_key`) map cannot hold both a retired and a currently-active key for the same identity, the combined key-resolver object constructed at boot and on any `ValidatorSet`/`IssuerRegistry` change exposes `resolve_node_key(node_id, at_timestamp) → public_key` and `resolve_issuer_key(issuer_id, at_timestamp) → public_key`, each selecting whichever key was active (per `retired_at`, where applicable) at the given timestamp. This resolver is injected into every call to Epic 2's FR-6 chain-validation function (chain sync per FR-3/FR-16, proposal validation per FR-10, and the validity cache backing `GET /node/info` per FR-26), passing each block's own `timestamp` as `at_timestamp` — Epic 2 itself never looks up keys from a registry or the network (dependency direction: Epic 3 → Epic 2 only).
24. **PoW proof-of-work target and difficulty verification (closes second-round MAJOR — PoW verification gap):** when invoking Epic 2's FR-6 chain-validation function for a PoW chain, the node supplies its own boot-configured `expected_difficulty` as an injected parameter. FR-6 then rejects any block where `sealed_consensus.difficulty` does not equal `expected_difficulty` (an arbitrary self-declared difficulty is not accepted) in addition to FR-6's own numeric target check (`block_hash`, as an unsigned integer, must satisfy the target derived from `sealed_consensus.difficulty`). This closes the gap where a fake, trivially-low-effort "PoW" chain could otherwise pass chain validation. **Changing the configured difficulty requires a fresh chain (v1.3 clarification):** because every block's `sealed_consensus.difficulty` must equal the network's `expected_difficulty`, changing the configured difficulty (e.g. to run a new comparative benchmark at a different difficulty) requires starting from a fresh chain/clean persisted store on every node in that network; restarting a node with a changed `expected_difficulty` against its OLD persisted chain (mined at the previous difficulty) will correctly fail FR-6 validation with `failure_type = "difficulty"` — this is expected/by-design behavior, not a bug to fix.
25. **Single validation checklist for proposals and sync (closes second-round MAJOR — commit_signatures at sync time):** the full Epic 2 FR-6 checklist — including, for PBFT chains, `commit_signatures[]` quorum verification (≥2f+1 valid signatures over the `ValidatorSet` injected per FR-23) — is the SAME checklist invoked both when validating an incoming block proposal in a live consensus round (FR-6/FR-10) and when validating a chain received via chain-sync (FR-3) or full-revalidation-on-divergence (FR-16), and when refreshing the validity cache that backs `GET /node/info`'s `chain_valid`/`first_invalid_index` fields (FR-20/FR-26). There is exactly one validation code path; chain-sync and `GET /node/info` MUST NOT use a lighter or partial check.
26. **Continuously-updated validity cache for `GET /node/info` (closes second-round MINOR — revalidation cost):** the node maintains a validity cache (`chain_valid`, `first_invalid_index`, and PBFT `quorum_status`) that is updated incrementally whenever a block is appended or the chain is replaced via sync (FR-3/FR-16) — using the same Epic 2 FR-6 checklist per FR-25 — rather than being recomputed by a full chain revalidation on every `GET /node/info` call. `GET /node/info` (FR-20) reads this cached state. This keeps the endpoint's cost independent of chain length, consistent with the pagination/cost-consciousness rationale behind FR-18.

### Non-functional requirements

- Communication transport is REST + WebSocket only, both used directly between peer nodes (no message broker). RabbitMQ (or any centralized broker) is explicitly rejected as transport — see Global Out-of-Scope.
- The network must run as truly separate processes/containers (Docker/docker-compose), not threads or async tasks within one process, so that network-partition and Sybil-style scenarios in Epic 5 are structurally real, not simulated.
- PBFT configuration must support the standard `n ≥ 3f + 1` node-count-to-fault-tolerance relationship; the default docker-compose topology must document its `n` and resulting `f`.
- Consensus finalization latency and PoW difficulty must be tunable via configuration without code changes, to allow reproducible comparative benchmarks for the thesis.
- Node-to-node messages must be authenticated at the application layer using Epic 2's signature primitives (a node signs its proposed blocks with its `NodeKeyPair`); unsigned or invalidly signed proposals must be rejected.
- **CORS (closes M-12):** the REST API must be configured with CORS to allow requests from Epic 4's frontend origin (a separate origin/port from the node API), since the web UI and node API are served as separate applications; CORS configuration must be tunable per environment (dev/demo) via config, not hardcoded to a single origin.
- **The chain is never empty (v1.2):** every node's local chain contains at least the deterministic genesis block (Epic 2 FR-1) from process startup; no code path (chain sync, pagination, `GET /node/info`, metrics) may assume or produce a zero-block chain state.

### Non-goals

- RabbitMQ or any other centralized message broker is explicitly out of scope as inter-node transport. It was evaluated during design and rejected: a broker reintroduces a centralized point of trust/failure that conflicts with the decentralized architecture under study and would undermine the validity of the Sybil-attack demonstration in Epic 5. This decision is not to be revisited without a new architecture review (cross-reference: Epic 1 research on decentralization principles).

### Acceptance criteria

- [ ] A docker-compose network of at least 4 nodes starts successfully, each node logs its `ValidatorSet` (`n`, `f`) at boot, and each node can reach all others via REST and via `PeerConnectionManager`'s outbound WebSocket connections.
- [ ] A document batch submitted to one node via `POST /documents` results in a new block that is finalized and visible (via chain-sync REST or WebSocket broadcast) on all other running nodes, under both PoW mode and PBFT mode.
- [ ] Under PBFT with n=4 (f=1), the network continues to finalize blocks correctly when 1 node is stopped/unresponsive (reported as a crash fault); it stops finalizing and reports loss of quorum (distinctly, not conflated with a Byzantine report) when 2 nodes are stopped.
- [ ] A PBFT node injected with a Byzantine peer that sends conflicting `prepare` votes to different peers is reported/logged as an equivocation/Byzantine event, distinguishable from a crash-fault report (verifies M-9 closure).
- [ ] Registering additional peers via `POST /peers/register` (growing `PeerInfo`) does NOT change the PBFT quorum threshold — quorum is verifiably computed only over the boot-time `ValidatorSet` (verifies C-4 closure).
- [ ] Under PoW, block finalization time visibly scales with the configured difficulty (higher difficulty → longer time-to-finalize), verifiable via the metrics endpoint, and per-node hash-rate is present in the metrics output.
- [ ] A node presented with a block that fails Epic 2's `proposer_signature`, hash-chain, or (PBFT) `commit_signatures` check rejects it and does not re-broadcast it.
- [ ] A chain-sync request presenting a chain that diverges from the local chain before the local tip triggers full chain revalidation from genesis, not incremental from-the-tip validation only (verifies M-14 closure).
- [ ] `GET /chain?from=&to=` returns only the requested block range and enforces the server-side max page size when a larger range is requested.
- [ ] `GET /node/info` returns all of `{node_id, algorithm, n, f, node_public_key, tip_index, chain_valid, first_invalid_index, quorum_status}` with correct values on a running node.
- [ ] `GET /documents/{hash}` returns a 404 (via the standard error envelope) for a hash not present on chain, and full lookup data for a hash that is present.
- [ ] A request with an oversized `metadata` field or a malformed hash field (not matching `^[0-9a-f]{64}$`) is rejected with a validation error in the standard `{"error": {...}}` envelope.
- [ ] Metrics endpoint returns per-block finalization time for both consensus modes, sufficient to produce the comparison charts required in Epic 5.
- [ ] A node's boot log includes its loaded `IssuerRegistry` (`issuer_id`) and confirms `ValidatorSet` entries support a `retired_at` field; after a simulated `NodeKeyPair` rotation (a validator's old key marked `retired_at`, new key active), blocks proposed/attested to BEFORE the rotation still pass Epic 2 FR-6 validation, with the resolver correctly returning the OLD (retired) key for those blocks' timestamps and the NEW key for blocks after the rotation — i.e. `resolve_node_key(node_id, at_timestamp)` is exercised with at least two different `at_timestamp` values straddling the rotation and returns two different keys (verifies FR-23's time-aware resolver contract).
- [ ] A PoW block whose `sealed_consensus.difficulty` does not match the network's configured `expected_difficulty` is rejected with `failure_type = "difficulty"`, even if its `block_hash` happens to satisfy that (wrong) declared difficulty's own target (verifies FR-24).
- [ ] Chain-sync validation (FR-3) and `GET /node/info`'s cached `chain_valid` (FR-26) both reject a PBFT chain whose `commit_signatures[]` do not meet the 2f+1 quorum over the `ValidatorSet` — verified by presenting a block with insufficient commit signatures via both paths and observing `failure_type = "quorum"` from both (verifies FR-25).
- [ ] Two competing, independently finalized PBFT blocks observed at the same height are never silently tie-broken by `block_hash`; the condition is logged/reported as a Byzantine-fault event (verifies FR-17's PoW-only tie-break scope).
- [ ] Submitting a `POST /documents` request whose `hash` already appears in a finalized block returns `409` via the standard error envelope; the response does not contain a re-used/duplicated `DocumentRecord` (verifies FR-22's duplicate-hash policy). Submitting a second `POST /documents` request with the same `hash` as one still sitting in the current pending batch/mempool (not yet finalized) likewise returns `409` (verifies FR-22's v1.3-broadened pending-batch/mempool check).
- [ ] `POST /documents` accepts only `{hash, metadata}` and rejects a request body containing a `signature` field with a validation error (verifies the unsigned-submission contract, FR-22).
- [ ] Repeated calls to `GET /node/info` on a large chain do not measurably scale in latency with chain length, consistent with reading from the FR-26 validity cache rather than recomputing full chain validation per call.

### Affected endpoints

New endpoints (all new — no prior API exists). **Revised in v1.1**: `POST /blocks/submit` renamed to `POST /documents`; `GET /documents/{hash}` relocated here from Epic 4 (was `GET /documents/search?hash=` under Epic 4 in v1.0); `GET /node/info` added. **Further revised in v1.2**: `POST /documents` now explicitly documented as accepting an UNSIGNED `{hash, metadata}` body, with the node producing the signed `DocumentRecord` server-side (see FR-22). All endpoints below use the FR-19 error envelope and Pydantic validation.

- `POST /peers/register` — register a peer node (`PeerInfo` registry only — never affects PBFT quorum, see FR-11).
- `GET /peers` — list known peers (`PeerInfo`).
- `GET /chain` — return full local chain, or a paginated range via `?from=&to=` (FR-18), with a server-enforced max page size.
- `POST /documents` (renamed from `POST /blocks/submit`) — submit an UNSIGNED `{hash, metadata}` pair for issuance; the node signs the resulting `DocumentRecord` server-side with its configured `IssuerKeyPair` before including it in a block (PoW: triggers local mining; PBFT: triggers a proposal round if the node is primary); rejects with `409` if `hash` already appears in any finalized block (see FR-22).
- `GET /documents/{hash}` (relocated from Epic 4, renamed from `GET /documents/search?hash=`) — look up a document record by hash; returns issuer, timestamp, block index, and Merkle-proof data if found, HTTP 404 if not.
- `GET /node/info` (NEW, closes M-10) — returns `{node_id, algorithm, n, f, node_public_key, tip_index, chain_valid, first_invalid_index, quorum_status}`.
- `GET /metrics/consensus` — return finalization-time and round-count metrics, including per-node hash-rate for PoW.
- `WS /ws/blocks` — real-time new-block broadcast channel.
- `WS /ws/pbft` — PBFT `pre-prepare`/`prepare`/`commit` message channel (may be merged with `/ws/blocks` depending on architect's decision).

### Schema changes

**Revised in v1.1** — replaces the v1.0 single `consensus_metadata` field with the Epic 2 preimage/attestation split, and adds the `ValidatorSet` entity (see also the top-level Schema Recommendations note):

- Consumes Epic 2's revised `Block` shape directly: the hashed preimage's `proposer_id` field (NEW in v1.2, see Epic 2 FR-2) carries the proposing node's `node_id` for BOTH algorithms; `sealed_consensus` inside the hashed preimage carries `{nonce, difficulty}` for PoW or `{view_number}` for PBFT (`primary_id` removed in v1.2 — `proposer_id` above is now the single source of truth for proposer identity); `commit_signatures[]` (PBFT only) is an attestation field attached after hashing, populated here by the PBFT commit phase, and is never part of the hashed preimage (see Epic 2 §Schema changes, C-2).
- New `ValidatorSet` record (NEW, closes C-4; field renamed in v1.3): `node_id` (**renamed in v1.3 from the stray `validator_id`** — this is the same identity concept used by FR-6/FR-11/FR-23 and by `PeerInfo` below; `node_id` is adopted network-wide as the single name), `node_public_key` (NodeKeyPair public key), plus network-wide `n` (total validators) and `f` (tolerated faults, `n ≥ 3f+1`). Static and loaded from boot-time config — never mutated at runtime, never derived from `PeerInfo`. Extended in v1.2 with a per-entry `retired_at` (nullable epoch-ms, NEW) field: when a validator's `NodeKeyPair` is rotated/removed, its old entry is retained with `retired_at` set (never deleted), so old blocks it produced/attested to remain verifiable by Epic 2 FR-6 (see FR-23), via the time-aware `resolve_node_key(node_id, at_timestamp)` resolver (v1.3).
- New `IssuerRegistry` record (NEW in v1.2; scope broadened in v1.3, closes second-round CRITICAL — key registries): `issuer_id`, `public_key` (IssuerKeyPair public key). Static, loaded from boot-time config. **v1.3:** this is a network-wide trust store covering every issuer identity used anywhere in the network — it both expresses which `issuer_id` this node signs new `DocumentRecord`s as via `POST /documents` (FR-22), AND backs verification of `DocumentRecord` signatures found in blocks from ANY node (Epic 2 FR-6's explicit signature-check step). For this thesis's scope the demo network uses a single shared `issuer_id`/key pair configured identically on every node, but the schema remains `issuer_id → public_key` generally for future multi-issuer support. Together with the `ValidatorSet.retired_at` extension above, this backs the injected, time-aware key resolver (`resolve_issuer_key(issuer_id, at_timestamp)`) consumed by Epic 2's FR-6 (see FR-23).
- `PeerInfo` record (clarified role, shape unchanged): `node_id`, `host`, `port`, `public_key` (NodeKeyPair public key), `last_seen`. Dynamic, gossip-populated, used only for connectivity/broadcast fan-out (`PeerConnectionManager`, FR-12) — explicitly never read for PBFT quorum counting.
- New `ConsensusMetric` record (persisted or in-memory, per node): `block_index`, `algorithm`, `proposed_at`, `finalized_at`, `attempts_or_rounds`, and (PoW only, closes Epic 5 M-8) `hash_rate` (node-local hashes/sec sample).

### UI changes

N/A directly — this epic exposes APIs consumed by Epic 4's web UI and Epic 5's testing/reporting scripts.

## 4. Epic 4: Web Interface (`Веб-інтерфейс (React)`)

### Feature description

A React single-page application that lets a user (acting as an issuing authority or a verifier) issue new documents onto the network built in Epics 2–3, verify an existing document by its hash, and visualize the current state of the blockchain (blocks, chain integrity, and — where applicable — per-node consensus status).

### User story

As an issuer, I want a web page where I can submit a document (or its hash) for issuance and see it confirmed on the blockchain, so that I have a simple way to demonstrate the issuance flow.

As a verifier, I want a web page where I can input a document's hash (or upload the document to have its hash computed client-side) and immediately see whether it matches a record on the chain, including issuer identity and issuance date, so that I can confirm authenticity without contacting the issuer directly.

As the thesis author, I want a visualization of the blockchain (blocks, links, and validity status) so that I can demonstrate the system's behavior live and use screenshots in the thesis.

### Functional requirements

1. **Issue page**: form to submit a document for issuance. The user either uploads a file (hash computed client-side via SHA-256, matching Epic 2's hashing) or pastes a pre-computed hash, plus minimal metadata (recipient identifier, document title). Submits to Epic 3's `POST /documents` (renamed from `POST /blocks/submit` — see Epic 3 §Affected endpoints, v1.1) as an UNSIGNED `{hash, metadata}` body (v1.2 — confirmed architectural decision: the node signs the resulting `DocumentRecord` server-side with its configured `IssuerKeyPair`; see Epic 3 FR-22). The browser never generates, holds, or transmits any issuer signature or private-key material — this is a hard constraint, not an implementation detail left open.
2. **Issue page**: after submission, the UI polls or listens (via WebSocket) for the block containing the submission to be finalized, then displays a confirmation with block index and hash. If the submission is rejected with `409` (duplicate `hash` already finalized on-chain — see Epic 3 FR-22), the UI surfaces this as a distinct duplicate-submission error, not a silent no-op or a masked retry.
3. **Verify page**: input a document hash (via file upload with client-side hashing, or manual hash paste). The UI queries the network via Epic 3's `GET /documents/{hash}` (see Affected Endpoints) and displays: found/not-found (a 404 response maps to "not found"), issuer identity, issuance timestamp, and containing block index if found.
4. **Verify page**: displays a Merkle inclusion proof result (valid/invalid) using Epic 2's proof-verification logic, either computed client-side against data returned by the API or verified server-side and reported as a boolean with supporting proof data.
5. **Chain visualization page**: renders the chain as a sequence of connected blocks (e.g., a horizontal chain diagram), each block showing index, timestamp, document count, and a validity indicator (valid/tampered) derived from Epic 2's chain-validation check.
6. **Chain visualization page**: when connected to a multi-node network (Epic 3), allows switching between nodes (by URL/selector) to visually compare each node's local chain view — useful for demonstrating consensus convergence or forks.
7. The UI must clearly label which consensus mode (PoW/PBFT) the currently viewed network is running, sourced from Epic 3's metrics endpoint.

### Non-functional requirements

- Client-side hashing (for file uploads) must use the Web Crypto API (SHA-256) so the browser never needs to transmit the raw file to the server unless explicitly required for optional IPFS storage (see Global Out-of-Scope — out of scope by default).
- Verify-page lookups must return a result within a few seconds under the demo network's expected load (tens of documents), sufficient for a live thesis defense demonstration — no formal SLA required given the academic scope.
- No user authentication/authorization system is required for this diploma prototype; the issuer role is assumed trusted for demonstration purposes (document this assumption explicitly — it is a deliberate scope reduction for an academic prototype, not a production system).

### Acceptance criteria

- [ ] A user can issue a document through the UI and see it confirmed with a block index once finalized, on both PoW and PBFT demo networks.
- [ ] A user can verify a previously issued, unmodified document and see a "valid" result with correct issuer and timestamp.
- [ ] A user can attempt to verify a document whose content was altered after issuance (same metadata, different bytes) and see an "invalid/not found" result, demonstrating tamper detection end-to-end through the UI.
- [ ] The chain visualization page correctly renders at least 5 sequential blocks and flags a chain as invalid when a block is manually corrupted in the backing store (used for a live tamper demo).
- [ ] Switching the node selector on the visualization page shows a different node's chain state without a full page reload.

### Affected endpoints

**Revised in v1.1:** the document-lookup endpoint is now owned and defined by Epic 3 (see Epic 3 §Affected endpoints) rather than introduced here — Epic 4 is purely a consumer of Epic 3's API, with no new endpoints of its own.

Consumes Epic 3 endpoints: `POST /documents` (renamed from `POST /blocks/submit`; v1.2: submits an unsigned `{hash, metadata}` body — the node signs server-side, see Epic 3 FR-22), `GET /chain` (now supports `?from=&to=` pagination), `GET /documents/{hash}` (relocated from this epic in v1.0 — was `GET /documents/search?hash=`; now returns issuer, timestamp, block index, and Merkle proof data, with a 404 for not-found), `GET /node/info` (new, for consensus-mode labeling per FR-7), `WS /ws/blocks`, `GET /metrics/consensus`.

### Schema changes

No new persisted schema; this epic is a client of Epic 2/3 data models. If optional IPFS support is added later, the Issue page would additionally display/store an `ipfs_cid` per Epic 2's optional field — explicitly deferred, not required for this epic's acceptance.

### UI changes

New pages/components (all new — first version of the UI):
- `Issue` page/form
- `Verify` page/form
- `ChainVisualization` page (with node selector)
- Shared `ConsensusModeBadge` component showing current network's active algorithm

## 5. Epic 5: Attack Resistance Testing (`Тестування стійкості до атак`)

### Feature description

A testing and reporting effort that exercises the network built in Epics 2–3 against two classes of attack — Sybil attacks (an attacker registers many fake/colluding nodes to try to bias consensus) and backdating/tampering of records (an attacker attempts to alter or insert a document record with a falsified issuance timestamp after the fact). Results (success/failure of each attack, and consensus performance data) are turned into comparison charts using matplotlib/plotly for the thesis write-up. This epic is a research/reporting deliverable — the charting tooling itself is not part of the running production-like system, only of the thesis evidence base.

**Revision note (v1.1, post architecture-review):** tamper-detection scripts must verify against an out-of-band trusted issuer public key, never against the attacked node's own key-store (closes M-2); the Sybil-resistance metric for PoW must be measured by hash-power share rather than node-count share, on a separate chart axis/panel from PBFT's node-count-based metric (closes M-8); Byzantine/adversarial node behavior must be implemented as a separate attacker component/image, not as flags inside the honest node's production code (closes M-13); and attack verification goes through Epic 3's API directly, not through Epic 4's UI via browser automation (MINOR — removes an unnecessary Epic 5 → Epic 4 dependency).

### User story

As the thesis author, I want reproducible attack scenarios run against both the PoW and PBFT configurations of my network, with the results captured as data and rendered as comparison charts, so that I can draw evidence-based conclusions about each consensus algorithm's attack resistance and performance for the thesis.

### Functional requirements

1. **Sybil attack scenario, separate attacker component (closes M-13)**: script(s)/component that spin up N additional attacker-controlled node containers (using Epic 3's docker-compose network) that register as peers and attempt to bias block finalization (e.g., flood proposals, vote as a colluding minority/majority block in PBFT, or out-hash honest miners in PoW at a controlled difficulty). Adversarial behavior (equivocation, vote withholding, message flooding) is implemented as a **separate attacker image/component** that imports Epic 3's consensus engine as a library and overrides the relevant behavior (e.g., subclassing/monkey-patching the message-handling hooks in the imported library) — it must NOT be implemented as environment-flag conditionals inside the honest node's production code path. The attacker image is built and deployed as its own docker-compose service, distinct from the honest-node image.
2. **Sybil attack scenario, algorithm-appropriate metric (closes M-8)**: measure and record the minimum attacker share needed to successfully disrupt consensus (e.g., cause a fork, stall finalization, or finalize an invalid block), using the metric appropriate to each algorithm's actual Sybil-resistance mechanism: for **PBFT**, the fraction of attacker-controlled *ValidatorSet* seats (node-count-based, since PBFT resistance comes from closed membership — Epic 3 C-4); for **PoW**, the attacker's **hash-power share** (NOT node count — PoW resistance comes from hash power, per-node hash-rate is recorded via Epic 3's `GET /metrics/consensus`, see FR-9 there). Validate results up to the theoretical limits already known from the literature (Epic 1). PoW and PBFT results are measured on different axes and must never be reported as directly comparable node-for-node figures.
3. **Backdating/tampering scenario, out-of-band trust anchor (closes M-2)**: script(s) that attempt to (a) alter a document record's timestamp or content directly in a node's persisted chain store, and (b) attempt to inject a new block into the middle of an existing chain with a falsified earlier timestamp. Detection is confirmed using Epic 2's chain-validation, and signature verification in these scripts is performed against a **separately-stored, read-only trusted issuer public key** (a trust-anchor config file maintained outside the attacked node's own key-store directory) — never by reading the `IssuerKeyPair` public key from the key-store of the node under attack, since an attacker with filesystem access on that node could swap both the record and the key together, invalidating the test. Verification is performed via direct calls to Epic 3's API (`GET /documents/{hash}`, `GET /chain`), not through Epic 4's browser UI (MINOR — removes the Epic 5 → Epic 4 dependency); an optional manual UI demonstration of the same tamper scenario remains valid as a separate, non-blocking illustrative step (see Epic 4 AC).
4. Record, for every attack run: attack type, consensus mode, attacker node/fraction (PBFT) or attacker hash-power share (PoW), outcome (detected/blocked vs. succeeded), and time-to-detection where applicable.
5. Produce comparison charts (matplotlib or plotly, exported as static images for the thesis document) covering at minimum: (a) PoW vs. PBFT block-finalization latency at varying network sizes/difficulties (sourced from Epic 3's metrics endpoint), and (b) Sybil-resistance thresholds shown as **two separate chart panels** — one for PBFT (x-axis: fraction of attacker `ValidatorSet` seats) and one for PoW (x-axis: attacker hash-power share) — never merged into a single node-count axis that would misrepresent PoW's actual resistance mechanism (closes M-8).
6. All attack scripts, the separate attacker image/component, and chart-generation scripts are documented (how to run, expected output) as part of the thesis appendix/repo, but are not required to be integrated into the Epic 4 web UI.

### Non-functional requirements

- Attack scenarios must run against the real Docker/docker-compose multi-node network from Epic 3 (not a mocked or single-process stand-in), so results are representative of the actual implemented system.
- Chart generation must be reproducible from raw recorded data (a script re-run on the same captured data produces the same chart), for thesis-defense reproducibility.
- No production security hardening is required beyond what Epics 2–3 already implement; this epic's job is to measure and report existing resistance/weaknesses, not to further harden the system (any hardening gaps discovered should be documented as findings, and only fixed if time permits — explicitly optional beyond the reporting deliverable).

### Acceptance criteria

- [ ] At least one successful and one unsuccessful Sybil-attack run is recorded for each consensus mode (PoW and PBFT), i.e., results show a clear threshold (PBFT: `ValidatorSet` seat fraction; PoW: hash-power share) or a documented reason none was found within tested bounds.
- [ ] The attacker component/image used in the Sybil scenario is a separate build artifact (its own Dockerfile/image) that imports and overrides Epic 3's consensus engine, verifiably NOT gated by an environment flag inside the honest-node image (verifies M-13 closure — inspect the honest-node image/codebase for absence of attacker-mode conditionals).
- [ ] The backdating/tampering scenario is demonstrated to be detected: (a) by Epic 2's chain-validation (direct chain-store tampering), verified against the separately-stored trusted issuer public key rather than the attacked node's own key-store (verifies M-2 closure), and (b) optionally by Epic 4's verify flow as a non-blocking manual demonstration.
- [ ] At least 2 comparison charts exist covering finalization latency and Sybil-resistance threshold, with PoW's threshold plotted as hash-power share and PBFT's plotted as `ValidatorSet` seat fraction on separate panels — never overlaid on a single shared node-count axis (verifies M-8 closure).
- [ ] Recorded PoW attack-run data includes a per-node hash-rate sample for every run.
- [ ] A written summary of findings (attack type → outcome → consensus mode) exists, suitable for inclusion in the thesis results chapter, cross-referencing Epic 1's research expectations against the measured results, and explicitly notes that PoW and PBFT Sybil-resistance are measured on different axes and are not directly comparable node-for-node.

### Affected endpoints

No new endpoints on the running system. **Revised in v1.1**: verification now goes through Epic 3's API directly rather than Epic 4's UI. Consumes Epic 3's existing endpoints: `POST /peers/register`, `POST /documents` (renamed from `POST /blocks/submit`), `GET /documents/{hash}` (relocated to Epic 3 in v1.1, replaces the prior `GET /documents/search` reference to Epic 4), `GET /chain`, `GET /node/info`, `GET /metrics/consensus`, `WS /ws/blocks`, `WS /ws/pbft`.

### Schema changes

No changes to the running system's schema. New standalone artifacts (outside the node's runtime schema): a results dataset (e.g., CSV/JSON) recording attack-run outcomes per FR-4, used only as input to chart generation.

### UI changes

N/A — no changes to the Epic 4 web UI. Charts are standalone image/report artifacts for the thesis document, not rendered in the live application.
